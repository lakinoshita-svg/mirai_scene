1．サービスの考え方

「好き・興味」を入口に、仕事のひと場面を選んで考える体験です。ガイダンス参加者と、進路ナビへ直接アクセスする学生の両方が利用します。適性診断や正解当てにはしません。

1体験は3シーン、各シーンは3選択肢です。選択後は、状況を整理する共通解説と、各案の説明・良い点・懸念点を表示します。

完了後の「どの部分が、ちょっと気になった？」は、感想を言葉にする手助けです。各場面に専用の振り返り文があります。「まだ、よく分からない」「少し違うかも」も選べ、選ばずに進めます。感想は保存・送信しません。

学校検索 →「分野探究する」→ 資料請求の説明 → 同分野の仕事体験 → 別の仕事体験の順で案内します。「探究」は機能名の名詞としては使わず、教材へ進む行動を「分野探究する」と表します。

2．制作と部署確認

  1. 体験の題材、件数、資料、確認担当者を決めます。通常は2〜5体験ずつ作ります。
  2. Codexへ制作引き継ぎガイドとAI向け仕様書を読ませ、下書き作成を依頼します。下書きは drafts/batch-NNN/ で管理します。
  3. 自社資料・進路ナビの情報を土台に、具体的な業務描写は厚生労働省job tagで確認します。資料本文を確認した日を記録します。
  4. 担当部署は文章・画像・学びの対応を確認します。AIの構造チェックと、実務内容の確認を区別してください。
  5. 確認者・確認日・未確認事項を記録します。承認のある原稿だけを公開用の編集元へ入れます。
  6. 制作担当が検証と配布物作成を行い、導入担当へ渡します。本番公開は導入先の手順で行います。

Codexへの依頼例

制作引き継ぎガイドとAI向け仕様書に従い、〇〇の体験を2件、下書きで作成してください。各3シーン・3選択肢と、場面ごとの振り返り文を用意してください。添付資料を確認し、不明点を確認記録へ残してください。公開元への反映は対象外です。

文章の確認基準

  • 選択前の状況に、判断に必要な条件がある。
  • 各案の良い点と懸念点が、場面の条件と結び付いている。
  • 振り返り文が場面ごとに異なり、気になった理由を本人の言葉の候補として示す。
  • 感情・性格・適性を断定しない。
  • 架空の設定と資料で確認できる事実を混同しない。
  • 確認していない資料日付や監修済みの表記を使わない。

3．Excelで原稿を確認する

  1. 配布された確認用Excelを部署名付きで保存します。
  2. 「確認対象一覧」で担当コンテンツIDを選びます。同じ職業の別体験は別IDです。
  3. 「原稿確認」をIDで絞り込みます。1行がJSONの1項目です。「体験後の振り返り文」も確認対象です。
  4. 原文・ID・JSON内の位置は保持し、「確認状況」「修正希望・理由」「確認者」「確認日」を記入します。
  5. 「連携設定確認」で、テーマ・分野・教材・学校検索・広告・地域の対応を確認します。空配列 [] は登録なしです。
  6. 記入済みExcelを制作担当へ返します。ExcelからJSONへの自動取り込み機能はありません。制作担当が指摘と現行原稿を照合して反映します。
確認状況意味
未確認未着手
確認中資料や部署内で確認中
修正依頼対象の文・希望する表現・理由を記入
確認済みその項目を確認した人と日付を記入

例：「結果を保証する表現を避け、条件によって結果が異なることを示してください」。確認済みは公開承認や専門家監修と同じ意味ではありません。

Excelは出力時点の原稿です。manifest.jsonの対象ファイル・SHA-256で原稿を照合します。再出力時の確認欄は未確認です。記入済みExcelは別途保管してください。

制作担当は npm run content:export-review を実行します。出力は outputs/operations/<UTC日時>/、Excel内の日付は日本時間です。対象は公開元JSONと連携設定で、下書きは通常出力に含みません。下書きの確認用Excelは対象を明示して依頼してください。

Excel出力にはCodex同梱のartifact-toolが必要です。依存の場所は CODEX_ARTIFACT_MODULE_ROOT で指定できます。npm run content:export-review -- --check は原稿読込と件数のみを確認します。

画像の管理

場面の観察や案の比較に必要な画像を使います。正誤マークや原因を断定する矢印は加えません。装飾だけを目的に全シーンへ画像を入れる必要はありません。

public/assets/ に画像を保存し、原稿の image.src と image.alt を設定します。比較は comparison を使います。ファイル名は用途の分かるキャメルケースを基本にし、公開URLの識別子は維持します。単独・比較画像は縦横比を保って表示します。

PC・スマートフォンで確認すること

  • 文字・画像・ボタンが切れず、横スクロールが出ない。
  • FVのCTAで一覧へ移動できる。
  • カテゴリー・キーワード検索・条件クリア・追加表示が動く。
  • 3シーンを完了でき、選択肢の説明を比較できる。
  • 感想ボタンで専用の文章が表示され、選び直せる。
  • 学校検索の分野パラメーターと、教材へのリンク先が正しい。

5．導入とZIPの受け渡し

配布対象：deliveries/release-2026-10-09/miraiSceneShinronavi20261009.zip。ZIPと同じフォルダのmanifest.jsonを一緒に渡します。制作元はGitHub、進路ナビ本体は別のGitLabです。コミットの直接取り込みは前提にしません。

  1. npm run content:verify で監査・型・ビルド・テスト・連携データを確認します。
  2. npm run build:shinronavi で本文・静的ファイル・PHP接続部品・マニュアルを生成します。integrations/shinronavi/output/latest.json で生成先を確認します。
  3. npm run release:package で、配布設定に従ってZIPを作成します。ZIP内の全ファイルと生成元を照合し、SHA-256をmanifestへ記録します。同名のZIPがある場合は停止します。
  4. 導入担当へZIP・manifestを渡します。ZIP内のINSTALL.mdに従い、検証環境へ配置してください。
  5. 進路ナビ本体のヘッダー・フッター・Tailwind・DB・ルーティングとの結合を確認します。
  6. 本番ファイルと設定をバックアップし、承認された一式を配置します。問題時は保存した一式へ戻します。

ZIPにはHTML・JSのほか、専用CSS・画像・一覧JSON・PHP・tpl・rewrite設定が必要です。Tailwindだけでは専用スタイルを代替できません。JSONだけの本番コピーでは反映されません。

固定配布物は上書きせず、版を指定して保管します。ZIPはGit対象外なので別途共有します。マニュアルや仕様書は公開領域へ置かず、配置対象はZIPの new/ 配下です。コンテンツだけを安全に自動更新する専用パッケージ・競合検出付き取り込みは未実装です。

7．困ったとき

症状確認すること
原稿が画面に出ない編集元・ビルド・配布版・配置先・キャッシュを確認します。
画像やCSSが404/mirai_scene/、rewrite、同一版の静的ファイルを確認します。
広告が出ない広告登録、enabled、categoryAds、地域条件を確認します。空の登録では非表示が正常です。
Excelの原文が合わないmanifestと対象原稿を照合して再出力します。
ロゴが見つからない生成本文にserviceIdentityが含まれ、専用CSSが読み込まれているか確認します。

詳細な配置手順は配布物のINSTALL.md、確認範囲はVALIDATION.mdを参照してください。
