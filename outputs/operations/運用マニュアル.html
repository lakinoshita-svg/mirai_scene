コンテンツ運用マニュアル

Codexで原稿を作成し、別部署がExcelで確認してから公開するための手順です。現在の出力対象は19コンテンツ・57シーンです。

更新の流れExcelの使い方確認基準公開作業設定と対応状況

1. 担当と更新の流れ

原稿の正本はJSONです。Excelの変更だけではサイトへ反映されません。Excelからの自動取り込みは実装していません。確認済みは内容確認の状態であり、公開済みを意味しません。

制作依頼の例

「○○の職業体験を作成してください。テーマは『しくみを考える』。高校生が知識なしでも考えられる3シーンにしてください。各設問に状況整理の共通解説、各選択肢に説明・良いこと・懸念点を入れてください。添付資料を基に業務描写を確認し、学び・探究・学校検索の対応を設定して、下書きと確認用Excelを作成してください。」

2. Excelで確認する

  1. 配布されたExcelを部署名付きの名前で保存します。原本を残してください。
  2. 「確認対象一覧」で担当するコンテンツIDを確認します。同じ職業の複数体験は別IDです。
  3. 「原稿確認」のフィルターでコンテンツIDを選びます。1行がJSONの1項目です。場面・選択肢欄でシーンと選択肢を識別できます。
  4. 原文は書き換えず、黄色の「確認状況」「修正希望・理由」「確認者」「確認日」を記入します。日付は年月日で記入してください。
  5. 「連携設定確認」は分野・テーマ・探究先・学校検索分野・広告・地域の対応を確認するシートです。空配列の [] は登録なしを表します。
  6. 記入済みファイルを制作担当へ返します。制作担当は対象IDとJSON内の位置を指定してCodexに反映を依頼します。
確認状況使い方
未確認まだ確認していない。出力直後の初期値
確認中調査や部署内の確認を進めている
修正依頼修正案と理由を記入。必要なら根拠資料のページやURLも記載
確認済みその項目の内容を確認した。確認者と確認日も記入

修正希望の例：「『必ず改善する』は断定が強いため『改善につながる場合がある』に変更。現場では条件で結果が変わるため。」変更なしでも、確認した項目には確認済みを記入してください。行の削除やID・JSON内の位置の変更は行わないでください。

再出力と版の管理

Excelは出力時点の控えです。更新時はCodexへ「最新JSONから確認用Excelを再出力して」と依頼します。日時別フォルダ内の別ファイルに出力され、確認欄は未確認から始まります。旧Excelの指摘は自動移行されません。元の確認ファイルを保管し、変更した項目を再確認してください。

出力時に同名のmanifest.jsonも保存します。対象ファイルとSHA-256で、どの原稿を確認したか照合できます。古いExcelを戻された場合は制作担当が原稿の変更有無を照合し、旧文で上書きしないよう差分を確認します。

Excelを再出力するコマンド

制作環境で npm run content:export-review を実行します。Codex同梱のartifact-toolを使用します。別端末で依存の場所が異なる場合は CODEX_ARTIFACT_MODULE_ROOT に同梱node_modulesの場所を指定してください。

出力先は outputs/operations/<UTC日時>/。Excel内の日付は日本時間です。npm run content:export-review -- --check で原稿の読み込みと件数のみ確認できます。画像を追加・変更した場合も再出力してください。以前配布したExcelには、今回追加した画像のパス・説明文が含まれていません。

シーン画像の追加・更新

画像は状況を観察する手がかりとして使用します。答えや原因を断定する矢印・正誤マークなどは加えません。画像が不要な会話・判断中心の場面には、装飾のためだけに追加しません。

追加した場面ファイル（public/assets/scenes/内）確認すること
美容師・シーン1beauty-reference.pngお客さまが持参した髪型の参考写真として読み取れるか
建築士・シーン3architect-entrance.png入口・案内台・通路の関係が伝わるか。寸法を保証する図面ではない

物流・シーン2logistics-box.png商品箱と配送箱、緩衝材の関係が伝わるか
  1. Codexへ対象のコンテンツID・シーンID・画像で見せたい状況を指定します。
  2. 作成した画像を public/assets/scenes/ に保存します。既存画像の差し替えは別名で作成すると変更を追跡できます。
  3. 該当シーンの image.src に assets/scenes/ファイル名.png、image.alt に画像の具体的な説明を設定します。
  4. 原稿と画像を照合し、PC・SPで全体が切れずに見えるか確認します。単独画像は縦横比を保ち、高さを自動調整して全体を表示します。比較画像にも固定高・最大高を指定しません。
  5. 原稿検証・再ビルド・Excel再出力を行います。生成画像は実在現場の記録写真として扱いません。

3. 原稿・画面の確認基準

  • ガイダンス参加者にも、進路ナビへ直接来た学生にも通じる表現である。
  • 職業を決めさせる診断ではなく、「好き・興味」を見つける体験になっている。
  • 問いが状況と結びつき、共通解説で目的・制約・問いの意図が伝わる。
  • 各選択肢に説明・良いこと・懸念点があり、単純な正解選びになっていない。
  • 業務描写は自社の書籍・進路ナビの知見を基に、必要な具体描写をjob tagで補う。資料を未確認のまま確認日や監修済みを記載しない。
  • 画像と選択肢が一致し、画像の説明文も適切である。画像ファイルは画面で別途確認する（Excelはパスと説明文を収録）。
  • カードテーマ・職業分野・学びの対応・学校検索先が内容に合っている。

2026年10月2日改稿：19職業・57シーンの状況を具体化しました。判断に必要な条件は選択前に示し、事実と推測、確認済みと未確認を分けます。各選択肢は問いに対する行動として比較できるようにし、良い点と懸念点を対応させます。資料確認日は実際に本文を再確認した8職業のみ更新しています。今回の改稿後に確認を依頼する場合は、JSONからExcelを新規出力してください。

4. 制作・公開担当の手順

  1. npm run content:new -- engineer new-slug などで下書きを作成します。drafts内は公開対象外です。
  2. JSON、画像、学びの対応を編集します。公開済みslugはURLなので原則維持します。同じ職業の別体験には新しいslugを割り当てます。
  3. 確認用Excelと画面を使ってレビューを実施します。src/content/careers内の原稿はビルド対象です。reviewStatusだけを変更して非公開にできるとは考えないでください。
  4. 承認された内容を反映し、npm run content:verify を実行。エラーを解消します。
  5. PCとSPで一覧・絞り込み・追加表示・全3シーン・完了画面・探究と学校検索のリンクを確認します。PCは9件、SPは8件ずつです。
  6. npm run build:shinronavi で進路ナビ用配布物を作成します。integrations/shinronavi/output/latest.json のdirectoryが最新配布先です。
  7. 配布物のINSTALL.mdに従い検証環境へ配置します。共通ヘッダー・フッター・Tailwindとの併存、URL・画像・CSS・404を確認します。
  8. 本番の現行ファイルと設定を保存し、同一リリースの配布物をまとめて反映します。公開URLで確認し、公開記録を残します。不具合時は保存した直前版へファイルと設定をまとめて戻します。

JSONだけを本番へコピーしても反映されません。生成済みのdistや配布物を直接編集せず、元データを修正して再ビルドします。進路ナビPHP組み込みでは通常のdistではなく、build:shinronaviの配布物を使用します。

7. 困ったとき

SPのカードで画像だけが大きく表示される場合は、共通カードに対する display:block!important などの上書きを確認します。TOP固有の競合指定は削除済みです。カード右下の矢印は廃止し、説明文の下の余白を縮めています。
