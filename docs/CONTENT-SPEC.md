# ミライシーン コンテンツ仕様 v1

基準日：2026-10-02。実装上の正本は `src/content.config.ts`。この文書は現在の動作と制作上の約束を記載する。仕様変更時は実装・この文書・確認用Excelの項目名を一緒に見直す。

企画の背景・判断基準・例・レビュー方法は [制作引き継ぎガイド](editorial/HANDBOOK.md) を参照。別担当者への依頼は [依頼テンプレート](editorial/REQUEST-TEMPLATE.md) を使う。

## 目的と対象者

高校生が「好き・興味」から仕事・学び・学校を知る選択型体験。進路ガイダンス参加者と、進路ナビを直接訪れた学生の双方を対象とする。参加経験を前提にしない。適性診断、職業の向き不向きの判定、正解を採点する教材ではない。

## 1コンテンツの単位と公開範囲

- 1 JSON = 1仕事体験 = 3シーン × 各3選択肢。約3分は目安で、実測保証ではない。
- 同じ職業の異なる題材を複数作れる。`name` と `category` は同じでもよいが、`slug` と体験の `entryTitle` は区別する。300件は300職業ではなく約300体験として数える。
- 公開元：`src/content/careers/*.json`。ファイル名は `<slug>.json`。全件がビルド対象。
- 制作中：`drafts/<batch-id>/*.json`。Astroの公開対象外。単に `reviewStatus` を変えても公開を止められない。
- 納品固定版：`deliveries/initial-2026-10-02/`。今後の原稿作成・通常ビルドと独立した導入用ZIPを保管する。

## JSON項目：体験全体

| 項目 | 必須・形式 | 用途・注意 |
|---|---|---|
| slug | 必須、英小文字で開始、英小文字・数字・ハイフン | URLの識別子。全体で一意。公開後は原則変更しない |
| order | 必須、0以上の整数 | 昇順、同値ならslug順。制作時は重複を避ける |
| name / category | 必須、空でない文字列 | 職業名と分野。categoryは共通広告設定のキーにもなる |
| entryTitle / description | 必須、文字列 | 同じ職業でも体験内容が分かる見出し・紹介文 |
| cardTheme | 必須、登録済みIDを1つ | カード画像・一覧のテーマ分類。テーマ定義から共通画像を使う |
| interests | 必須、登録済みIDの配列、1件以上 | 関連性の補助情報。カードの主テーマと混同しない |
| word / color / ink | 必須、文字列 / 6桁HEX色 | 既存互換の項目。カードの共通画像はcardThemeで管理するため、新しい職業ごとのカード画像を増やさない |
| estimatedMinutes | 必須、正の整数 | 現在は3。所要時間・シーン数の案内はカードごとでなく共通説明に置く |
| studies / learning | 必須、1件以上の文字列配列 / 文字列 | 関連する学びと案内文。学科や資格で就職を保証しない |
| learningIds | 必須、登録済みIDの配列、1件以上 | 学び別一覧・探究・学校検索の対応表を参照する |
| image | 任意、src・alt | 体験全体の画像 |
| mission / brief | 任意、両方セット | 依頼文とrole・audience・goal・constraint（各必須文字列） |
| scenes | 必須、ちょうど3件 | 下表。シーンIDは体験内で一意 |
| reference | 必須 | title・publisher・httpsのurl・checkedAt（YYYY-MM-DD）・background |
| reviewStatus | 必須 | editorial-draft または reviewed。公開制御とは独立 |
| review | reviewedの場合必須 | reviewer・reviewedAt（実在する日付）・scope。未実施の確認や監修を書かない |

すべての本文文字列は空欄不可。`【要編集】` が残る原稿はビルドでエラーになる。reference.checkedAtは書式検証のため、日付の実在性と実際の確認の有無は編集時にも確認する。

## JSON項目：シーンと選択肢

| 項目 | 必須・形式 | 書く内容 |
|---|---|---|
| id | 必須 | scene-1〜scene-3を制作規約とする（実装は一意な文字列） |
| title | 必須 | 今回考える場面の短い見出し |
| situation | 必須 | 担当する立場、目的、分かっている条件、未確認の点。回答に必要な条件を先に示す |
| question | 必須 | いま何について選ぶのか。状況と選択肢の行動が対応する問い |
| contextExplanation | 必須 | 全選択肢共通の状況整理。制約と問いの意図を説明し、正解を決めつけない |
| options | 必須、3件 | id・label・explanation・benefit・caution（すべて必須文字列） |
| options[].id | 必須 | option-1〜option-3を制作規約とする。シーン内で一意 |
| options[].label | 必須 | 取る行動。3案の違いが読み取れる表現 |
| options[].explanation | 必須 | その行動で何をするか・何を確かめるか |
| options[].benefit | 必須 | この場面で期待できる良い変化。成果を保証しない |
| options[].caution | 必須 | その方法の限界と追加で確かめること。選んだ人を否定しない |
| perspective / insight | 必須 | 振り返る仕事の視点 / 短い気づき。選択結果の適性スコアではない |
| workConnection | 必須 | 業務背景と教材の対応を編集者向けに記録。個別シーンの出典枠として表示しない |
| image | 任意 | src・alt。画像を見て判断する必要がある場面に使う |
| comparison | 任意、2〜3枚 | 各src・alt・caption。比較する条件・違いが本文と一致すること |

画像srcは `assets/...` から始まる英数字・スラッシュ・ハイフン・アンダースコアのパスで、png/jpeg/jpg/webp/svgが使用可能。実体は `public/assets/`。先頭の `/` や外部URLを付けない。altだけで正解や画像から分からない原因を断定しない。imageとcomparisonの併用はスキーマ上可能だが、制作上は必要性を見て選ぶ。

文章量は固定字数の制限を実装していない。目安は状況80〜140字、選択肢15〜40字、各説明40〜100字、共通解説100〜180字。字数を埋めることを目的にせず、SPで読み切れるか確認する。

## 画面の動作

1. 全員が同じ3シーンを順に体験する。回答によるシーンの分岐はない。
2. 1つ選んで解説を開く。共通解説、選んだ行動の説明・良い点・懸念点を確認し、他の選択肢も比較できる。
3. 解説表示後はその回答を変更できない。3シーン後に振り返りへ進む。
4. 回答はページ内だけに保持し、サーバー送信や永続保存をしない。再読み込みで最初からになる。
5. 完了後は関連する学び・探究・学校検索へ進める。選択したA/B/Cから職業適性や学校順位を計算しない。

## 分類・連携

| 定義 | 管理場所 | 現行仕様 |
|---|---|---|
| 4テーマ | src/data/interests.json | make＝つくる・表現する、support＝人の役に立つ、solve＝しくみを考える、discover＝知らない世界に触れる |
| テーマ追加 | 同上＋public/assets/interests | 定義と画像を追加し、選択・表示を確認。4テーマ固定の分岐を原稿に作らない |
| 探究・学校検索 | src/data/learning-links.json | learningIdsからlessonsとschoolFieldsを参照。学校検索のfld[]は確認済みIDを使い、推測して追加しない |
| 共通広告 | src/data/school-ads.json | 同じcategoryに共通の広告候補。職業ごとの重複登録を不要にする。新categoryはcategoryAdsにも登録 |
| 地域 | src/data/ad-regions.jsonほか | 手動選択／設定済みAPIの概略推定。正確な住所を取得する仕様ではない。未設定時は全国向けにフォールバック |

現状は広告実データ・自社IP API・本番探究への戻り導線などに別途導入作業がある。コンテンツ追加だけでこれらが稼働するとは扱わない。

## 一覧と300件への対応

PCは9件、650px以下は8件から開始し、同じ件数ずつ追加する。本文を含まない検索索引と必要なカードHTMLを取得する。テーマ・分野・検索で絞り込み、分類や画面幅区分が変わると初期件数に戻る。全詳細ページは静的生成。

1件増やすたびにUIコードを増やす必要はない。ただし約300件を公開するときの実サーバー配信速度、コンテンツの重複、探しやすさは別途確認する。既存の300件ベンチマークは性能検証であり、300件の原稿制作完了を意味しない。

## 編集基準と変更の扱い

自社書籍・進路ナビの知見を基盤とし、実務の具体描写はjob tag等の一次資料で補う。確認した資料の範囲と独自の教材設定を区別する。出典説明はaboutへ集約し、各設問に資料枠や監修未実施の表示を戻さない。

少量バッチごとに、状況→問い→3案→共通解説→各説明の整合を読み合わせる。「どの仕事でも使える相談・記録の話」だけにせず、対象物、判断材料、制約を具体化する。危険な行為を比較対象にせず、観察と原因の断定を区別する。

| 変更 | 手順 |
|---|---|
| 文章・既存分類での体験追加 | 下書き作成→一次資料確認→隔離ビルド→内容確認→公開元へ移す→content:verify→新しい配布版 |
| テーマ・学び・広告分野の追加 | 対応する定義・画像・検索先を追加し、既存体験と連携先への影響を確認 |
| 必須項目変更・シーン数変更・回答分岐 | v1の原稿を量産する前に仕様改訂。スキーマ・画面・JS・Excel出力・テスト・既存JSONの移行を同時に計画 |

固定した初期導入ZIPは上記作業で更新しない。将来の公開更新は別名の配布物を作成し、本文・索引・CSS/JS・画像を同じビルドでまとめて反映する。現時点ではJSONだけを本番へ差し替える方式ではない。
