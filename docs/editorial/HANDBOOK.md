# ミライシーン 制作引き継ぎガイド

版：1.0／更新日：2026-10-02。過去のチャットを読めない担当者が、同じ企画意図と確認基準で制作するためのガイド。

このガイドは判断の差を減らすためのもの。生成する文章の完全一致や、資料を読むだけでの品質保証はしない。共通の仕様・例・レビュー記録を使い、違いが出たときに理由を確認できるようにする。

## まず理解すること

### 感想を言葉にする文章

各シーンに `reflectionResponse` を書く。体験後の「どの部分が、ちょっと気になった？」では `insight` がボタン名、`reflectionResponse` が選択後の文章になる。

文章は「その場面のどこを気にしたか」と「それを本人がどう言葉にできそうか」を結ぶ。例：駅のポスターなら「自分が好きな見た目と、一瞬見て伝わる見た目は同じとは限らない。通学中ならどこを見るだろう」。締め切り前の追加依頼なら、紙面に残す情報を考える気持ちを扱う。同じ職業でも、準備・伝え方・制約への関心を区別する。

本人の気持ちを断定せず、解説や正解の押し付けにしない。別シーンにそのまま流用できる文章は、場面とのつながりを見直す。3つのボタンを順に押して読み比べる。職業の事実を追加する場合は、通常の資料確認も行う。

教材本文へ進む行動名は「分野探究する」。機能を名詞の「探究」とは呼ばない。

進路ナビのコンセプトは「“好き”から始まる進路選び」。やりたい仕事が決まっていない高校生が「少し気になる」から試せる体験をつくる。仕事の名前を覚えさせるより、実際の仕事で考えることを知り、学びや学校を調べるきっかけをつくる。

学校の進路指導では、適性・適職診断、教材、ガイダンス、ミライシーンという活用が想定される。ただしこれは利用例であり、必須の順番ではない。ガイダンスと関係なく進路ナビを訪れた学生にも通じるコピーにする。

期待する読後の気づきは「相手の話を聞いて形にするのが面白そう」「数字の違いを確かめるのが気になる」など。回答から「あなたはデザイナー向き」「この学校が最適」と判定しない。

## このプロジェクトで決まっていること

以下は会話で決まった方針の整理。新たな提案とは分けて扱う。

| 方針 | 理由・制作への影響 |
|---|---|
| AIで事前制作したJSON・画像を配信する | 閲覧ごとの生成費用と内容の揺れを避ける。リアルタイム生成に変更しない |
| ガイダンス参加者と一般訪問者の両方が対象 | 「ガイダンスで気になった仕事」のような参加前提の表現を使わない |
| 共通解説は状況の整理を含める | 選択肢の説明だけでは問いの意図が通じにくかったため |
| 各案に説明・良い点・懸念点を書く | 正解を示さず、選んだ行動から何が期待でき、何が残るかを伝える |
| 職業紹介は自社ナレッジを土台にする | 自社書籍・進路ナビと、job tagによる業務の具体描写を組み合わせる |
| 出典の公開案内はaboutへまとめる | 各設問の資料枠・資料確認日・監修未実施表示は削除済み。復活させない |
| 試作版の注意書きは削除済み | 読者向け画面へ再追加しない。編集上の確認状態はデータと記録に残す |
| 一覧のカード画像は4テーマで共通化 | 職業ごとに画像や表示テーマを作り分けない。5つ目以降を追加できる構造は維持 |
| 約3分・3シーンは共通説明で伝える | カードごとの繰り返し表示へ戻さない |
| 画像は判断に役立つ場面で使う | 特にデザイン比較は画像が必要。全場面への装飾画像の追加は不要 |
| 同じ職業で複数体験を作れる | nameとcategoryは共通でよい。slugと題材・見出しを区別する |
| 広告はcategory単位で共通化 | 同じ分野の複数体験に共通の学校広告を出す。回答で適性広告を決めない |
| 教材と学校検索につなげる | learningIdsの既存対応を使う。学校検索の分野IDを推測しない |
| 地域は利用者の負担が少ない概略で扱う | 正確な住所の入力や位置情報取得を原稿の前提にしない |
| 約300体験へ少量ずつ増やす | 仕様の問題を小さい段階で発見する。現行の基本単位は3シーン×3案 |
| 導入版と追加制作を分離する | 固定ZIPを維持し、追加はdraftsへ。GitHubとGitLabは別管理 |

学校や広告への導線を強めるために、特定の選択を高く評価したり、不安をあおって資料請求させたりしない。体験した行動→関係する学び→学校を調べる、という内容上のつながりをつくる。

## 正本と情報の探し方

### 体験完了後の感想と導線（2026-10-02更新）

感想ボタンは、何が分からないかも言葉にできない利用者が、小さなアウトプットを通じて体験を理解するために置く。返答は気持ちを代弁する言葉にし、本人の感情・適性を断定したり、直ちに学校探しを促したりしない。選び直し・未選択を許容する。

学びの説明の後は、学校検索→関連する教材へのリンク→資料請求の説明→同分野の教材・仕事体験一覧→別の興味につながる体験の順にする。「学校によって学べる内容や課程は異なります。今の選択から適性を判定したおすすめではありません。」という注意書きは完了画面へ再追加しない。適性判定をしない設計自体は維持する。

| 知りたいこと | 読むファイル |
|---|---|
| 項目・画面の現在仕様 | [CONTENT-SPEC-AI.md](../CONTENT-SPEC-AI.md)、実装は `src/content.config.ts` |
| 自社資料の原文 | [company-career-material.txt](company-career-material.txt) |
| 資料がその職業を扱っているか | [source-mapping.md](source-mapping.md) |
| 実際の原稿 | `src/content/careers/`、制作中は `drafts/` |
| 制作状況・重複 | [CONTENT-BATCHES.md](../CONTENT-BATCHES.md) |
| 出典と監修の記録 | [CONTENT-REVIEW.md](../../CONTENT-REVIEW.md) |
| 別部署レビュー・Excel | [CONTENT-OPERATIONS.md](../../CONTENT-OPERATIONS.md) |
| 配布範囲とGitLabへの受け渡し | [DELIVERY-AND-CONTENT.md](../DELIVERY-AND-CONTENT.md) |

自社資料はリポジトリ内に保存しているので、特定担当者のDownloadsや過去チャットの添付パスを前提にしない。書名・版・原本ページは未確認のため創作しない。一般図書館司書と司書教諭、農業生産者と農業技術者など、似た名前でも業務範囲が異なる。対応表の「関連職」「該当なし」をそのまま尊重する。

資料に記載がない内容まで「自社資料に基づく」と表現しない。必要な一次資料を読み、確認できた業務と教材で設定した日数・人数・依頼を分ける。参照できない資料はURLだけで確認済みにしない。

## 制作の順番

1. 依頼範囲とバッチを決め、台帳・既存題材を確認する。異なる職業名に言い換えただけの重複を避ける。
2. 職業の役割・仕事の対象・関係者を資料で確認する。本文のどの説明がどの業務を支えるか、レビュー記録に残す。
3. JSONを書く前に「誰が／何を／誰のために／どの条件で／何を判断する」を短く設計する。
4. 3シーンの流れを設計する。準備→調整→振り返りは一例であり、全職業へ同じ型を機械的に当てはめない。同じ設定を引き継ぐ場合は期限・場所・依頼の矛盾を確認する。
5. 各問いに3つの行動を置く。どれも現場で取り得る案とし、注目する情報・進め方・確かめ方の違いをつくる。
6. 状況の共通解説、各行動の説明・良い点・懸念点を記入する。条件が不足したら解説だけで補わず状況文を直す。
7. 判断に画像が必要か決める。画像がなければ比較できない設問を文章だけで完成扱いにしない。
8. 主テーマ・分野・学び・出典を登録する。既存IDを使えるか先に確認する。
9. 下記基準で自己レビューし、修正点と未確認事項を記録する。下書きを隔離ビルドし、画面を確認する。実行できなかった確認を成功扱いにしない。
10. バッチの台帳と確認記録を更新して渡す。制作のみの依頼で公開や固定ZIPの更新まで行わない。

## 書き方の基準

### 状況と問い

高校生が専門知識なしで判断を始められるようにする。専門用語が必要なら、例えば「ラフ（仕上がりを相談するための簡単な案）」のようにその場で分かる表現にする。幼い口調や、常に「すごい」「ワクワク」と評価する文章は使わない。

「仕事で困りました。どうしますか？」では不足する。対象物と期限、相手、未確認の点まで具体化する。ただし細かい条件を詰め込みすぎず、選択に関係するものを残す。

### 3つの案

「調べる／相談する／頑張る」のような抽象語だけで終わらせない。何を誰と調べるか、何が分かるかを書く。「準備する／危険を無視する／放置する」のように正解が明らかな並びにしない。

複数の案が併用できること自体は問題ない。その場合は「最初に注目したいのは？」「相談に向けてどこから整理する？」と問いの段階をそろえる。安全確認や必要な連絡など、全案に共通して必要なことを一つの任意選択肢に押し込めない。

### 解説の役割分担

| 欄 | 答えること | 避ける書き方 |
|---|---|---|
| 共通解説 | 何が問題で、どの条件を考える場面か | 特定の案が正解だと誘導する |
| 説明 | 選んだ行動は何をする方法か | labelの言い換えだけ |
| 良い点 | この場面で何が見える・進めやすくなるか | 「成功します」「売上が上がります」などの保証 |
| 懸念点 | 何は分からず、何を追加確認するか | 「気をつけましょう」で終える、人格を評価する |
| 振り返り | どんな仕事の視点に触れたか | 「あなたはこの職業に向いています」 |

懸念点を付け足しただけで不適切な行動を正当化しない。知識が必要な危険作業の手順を試させるのではなく、現場条件の確認や担当者との調整として設計する。

## 共通の基準例：デザイナーの最初の30分

以下は構成をそろえるための編集例。新しい事実の出典や、全職業へコピーする定型文ではない。既存の [designer.json](../../src/content/careers/designer.json) scene-1を併読する。

**状況**：高校生向けイベントのポスターを依頼された。完成まで2日。「目立つものに」と言われている。打ち合わせへ向け、最初の30分をどう使うか。

**問い**：打ち合わせで方向を確かめるために、何から取りかかる？

| 案 | 説明 | 良い点 | 懸念点 |
|---|---|---|---|
| 参考例を集める | 掲示場所や見る人に合いそうな表現を選び、理由を整理する | 色や雰囲気の好みを具体物で比べられる | 探し続けると制作時間が減る。必要な情報の優先順位は別途確認する |
| 依頼者へ確認する質問を整理する | 誰に何を伝えるか、掲載必須の情報を確かめる準備をする | 日時や参加方法などを抜かさず構成できる | 質問だけでは完成像は伝わらない。次に配置案を示して認識をそろえる |
| 簡単な配置案を作る | 見出し・日時・写真の仮配置で反応を確かめる | 「日時を大きく」など具体的な会話につながる | 前提が違えば作り直しになる。30分で仕上げようとせず確認点を絞る |

**共通解説の例**：完成まで2日なので、「目立つ」の意味が曖昧なまま細部を作ると、後から大きな修正が必要になるかもしれません。ここでは、限られた時間で何を確かめるかを考えます。参考例、質問、配置案のどの方法でも、打ち合わせで知りたいことを決め、制作と確認の時間を残しましょう。

この例が成立する理由は、3案が同じ目的に向かい、得られる情報と残る不確実さが違うこと。「計画すれば成功する」という一般論だけでは、デザインの仕事を体験したことにならない。

## 差が出やすい箇所と直し方

| 避けたい例 | 修正の方向 |
|---|---|
| 「先輩に相談すると安心です」 | 何を見せ、どの条件を相談し、次の判断にどう使うかを書く |
| 問いは「今すぐ直すなら？」なのに一案だけ「後で調査する」 | 同じ段階の案にそろえるか、「改善へ向け何から進める？」へ問いを修正 |
| 解説で初めて「明日が締め切り」と明かす | 締め切りを状況文へ出し、選ぶ前に比較可能にする |
| 「雨の日に残ったので雨が原因」 | 観察と原因を分け、曜日・製造数など他の条件も確かめる |
| 「紙を選んだから制作が好きになった」 | 観察できた行動を伝え、一場面だけで気持ちや成長を断定しない |
| 「引用元の職業名が似ているから同じ仕事」 | 施設・役割・担当範囲を照合し、違いは編集用記録に残す |
| 「小さい箱ならコスト削減で正解」 | 商品の保護、梱包時間、資材などの条件も含めて比較する |
| 画像はA案が華やか、altに「読みにくい失敗例」と書く | altは見える特徴を説明し、評価を先に与えない |
| 関連学科を思いつきで増やす | 学ぶ内容と体験の行動の接点を説明できるものを既存対応表から選ぶ |

## レビューの共通判定

以下はこの引き継ぎで導入する制作上の基準。専門家監修や公開承認の代わりではない。各項目を「適合／要修正／未確認」で記録し、本文の該当箇所と理由を書く。合計点によって重大な問題を相殺しない。

| 観点 | 適合の条件 |
|---|---|
| 対象・目的 | ガイダンス未参加でも理解でき、好き・興味を見つける体験になっている |
| 業務の範囲 | 資料と役割・対象物が対応し、資料にない保証や権限を足していない |
| 状況の十分さ | 判断に必要な条件を選択前に読める。3シーンに矛盾がない |
| 案の比較 | 3案が問いに答え、それぞれ取り得る行動で、単なる言い換えではない |
| 解説の因果 | その行動→期待できる変化→残る懸念が今回の条件でつながる |
| 仕事らしさ | 職業名を別のものに替えるだけでは成立しない対象物や判断材料がある |
| 読みやすさ | 専門知識なしで入口が分かり、SPでも必要以上に長くない |
| 画像 | 必要性が判断され、使用時は本文・比較条件・altが対応する。不要なら理由を記録 |
| 学びへの接続 | 学びの説明が体験と関係し、登録済みID・学校検索先と一致する |
| 証跡・実装 | 出典確認日が実際の確認を示し、レビュー記録と台帳、JSON検証の結果が残る |

要修正は直して再確認する。未確認は理由と影響する文を明記し、そのまま完成・監修済みとは報告しない。資料未確認、業務範囲の不一致、事実の断定、明らかな不適切行為、schema不一致が残る原稿は下書きとして扱う。確認依頼は問題の文と修正候補を添えて具体的にする。

担当交代時は、まず既存のdesigner scene-1とdata-scientist scene-2を両者がこの基準で読み、判定理由を比べる。次に少量バッチを制作し、基準の解釈が合ってから増やす。別担当者がいない場合は自己レビューと明記し、独立レビューを受けたとは書かない。

## 渡す成果物と引き継ぎ

- 原稿JSONと必要な画像。原稿以外に変更した定義があれば、その理由と影響範囲。
- バッチごとのREVIEW.md：資料、独自設定、各基準の判定、修正内容、未確認事項、実施したコマンド。
- 制作台帳：件数、slug、仕様版、状態。将来の予定と完成した原稿を混ぜない。
- 引き継ぎ要約：次に読むファイル、次の具体的な作業、止めている理由。チャット履歴だけに判断理由を残さない。

別の環境には最新のリポジトリ一式と今回の依頼を渡す。文書だけの場合は原稿・画像・定義・資料原文も必要。ソース資料の社外共有可否は所属組織の運用に従い、公開サイトへ原文を転記しない。固定導入ZIPはGit対象外なので、導入担当へは必要に応じて別途渡す。

新しい合意が出たら、決定日・理由・影響ファイルを残し、このガイドと仕様を更新する。実装と文書が食い違う場合は、現在動く挙動と意図した挙動を分けて報告し、推測で方針を変更しない。

## 用語の方針 2026年10月7日

「探究」は広い意味と深く学ぶ活動を含むため、機能名・コンテンツ名・見出しとして名詞で使用しない。画面では内容に合わせて「学びの分野」「この分野で学ぶこと」「関連する教材」「教材を読む」など、遷移先が分かる表現を使う。「探究する」という動詞としての使用は可能。

制作する画面・文章・企画書・マニュアルに適用する。引用元の原文や正式名称、過去の確認記録・固定配布物は改変しない。公開URLのexplore、内部のinquiry、教材slugなどの識別子は変更せず、表示名称と分けて扱う。
